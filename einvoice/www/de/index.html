einvoice / Deutsch

E-Rechnungen offline validieren

einvoice prüft elektronische Rechnungen gegen die Geschäftsregeln von EN 16931 und der deutschen XRechnung — als Kommandozeilenwerkzeug, komplett offline, mit null Abhängigkeiten (reine Python-3-Standardbibliothek: kein Java, kein Saxon, keine Schematron-Toolchain, kein Netzwerkzugriff). Diese Seite ist der deutschsprachige Schnellstart: was das Werkzeug ist, was es ehrlich abdeckt, und wie Sie es installieren, eine erste Rechnung prüfen und als CI-Gate verdrahten.

Was das Werkzeug ist

Ein Konformitätsprüfer für E-Rechnungen im Format UBL 2.1 Invoice oder UN/CEFACT CII, mit den Profilen en16931 (europäischer Kern) und xrechnung (Kern plus die deutsche KoSIT-Schicht: BR-DE-*-Regeln wie Leitweg-ID/Käuferreferenz, Verkäuferkontakt, Zahlungsangaben, Skonto-Grammatik). Insgesamt setzt der Prüfer 288 Geschäftsregeln durch; jede ist differentiell gegen die offiziellen CEN-/KoSIT-Schematron-Artefakte bewiesen, mit 0 Abweichungen. Das Ergebnis kommt dreifach: als menschenlesbare Zusammenfassung, als Exit-Code (das, worauf ein CI-Gate reagiert) und als --json-Maschinenprotokoll.

Die Fehlermeldungen gibt es auch auf Deutsch: mit --lang de zeigt die CLI zu jeder Regel den deutschen Korrekturtext — wo das offizielle KoSIT-Artefakt einen deutschen Text mitliefert, exakt diesen; sonst eine klar als Übersetzung gekennzeichnete Fassung, die nie als amtlicher Text ausgegeben wird.

Ehrliche Abdeckung: was ein grünes Ergebnis bedeutet

Ein grünes Ergebnis heißt: keine implementierte fatale Regel hat ausgelöst. Es heißt nicht „rechtsverbindlich konforme XRechnung“. Die Grenzen im Einzelnen:

  • 8 offizielle BR-CL-*-Codelisten-Prüfungen sind bewusst zurückgestellt und als dokumentierte Ausnahmen geführt — nicht als Abdeckung gezählt.
  • Eine strukturelle XSD-Validierung findet nicht statt; geprüft werden die Geschäftsregeln, nicht das Schema. Ein UBL-CreditNote-Wurzelelement wird nicht unterstützt.
  • 4 offizielle Regeln (BR-CO-05–BR-CO-08) sind in den CEN-Artefakten selbst als test="true()"-Tautologien ausgeliefert — sie können nie auslösen und sind deshalb nicht implementierbar; jede andere auslösbare offizielle BR-*-Regel ist implementiert oder eine dokumentierte, begründete Ausnahme (maschinell geprüfte Lücke: 0 in beiden CEN-Syntax-Universen).
  • Von den PEPPOL-EN16931-R*-Regeln ist genau die Teilmenge implementiert, die KoSIT im offiziellen XRechnung-Artefakt mitliefert (21 Regeln) — das ist keine Peppol-BIS-Billing-3.0-Unterstützung.

Nichts davon müssen Sie glauben: Das maßgebliche Regelinventar mit jeder Ausnahme und wörtlichen Artefakt-Belegen ist die Abdeckungsmatrix (COVERAGE.md) im Repository, und jede Zahl auf dieser Seite lässt sich dort nachrechnen. Lassen Sie vor dem tatsächlichen Einreichen trotzdem den offiziellen Validator Ihres Empfängers laufen — dieses Werkzeug ist der schnelle Vorab-Check, der die typischen Fehler früh fängt.

Installation und erste Prüfung

Alles Folgende läuft aus dem einvoice/-Verzeichnis eines Repository-Checkouts — offline, ohne weitere Installation. Die beiden Beispielrechnungen liegen im Repository: eine gültige XRechnung (fixed.xml) und dieselbe Datei mit zwei entfernten Pflichtangaben (broken.xml: ohne Käuferreferenz BT-10 und ohne Verkäuferkontakt BG-6).

1. Direkt aus dem Checkout — nichts zu installieren

python3 einvoice.py validate --profile xrechnung examples/01-missing-fields/fixed.xml

Die gültige Rechnung endet mit Exit-Code 0. Wer stattdessen das einvoice-Kommando im PATH will, installiert das Paket (null Laufzeitabhängigkeiten, dependencies = [] in pyproject.toml) und ruft es direkt auf — derselbe Codepfad, bestätigt per Test:

python3 -m pip install .
einvoice validate --profile xrechnung examples/01-missing-fields/fixed.xml

2. Eine kaputte Rechnung fällt durch — mit Regel-ID

python3 einvoice.py validate --profile xrechnung examples/01-missing-fields/broken.xml

Exit-Code 1; die Ausgabe nennt die erste verletzte fatale Regel (BR-DE-2, fehlender Verkäuferkontakt) samt betroffenem Element. Die Exit-Codes sind der ganze Vertrag, den ein CI-Gate braucht: 0 = keine implementierte fatale Regel verletzt, 1 = mindestens eine fatale Verletzung, 2 = Bedienfehler, 3 = kein wohlgeformtes XML.

3. Maschinenlesbar: --json

python3 einvoice.py validate --json --profile xrechnung examples/01-missing-fields/broken.xml

Gibt das vollständige Ergebnis als JSON auf stdout aus (Exit-Code unverändert 1): hier alle drei Befunde — die zwei fatalen Regeln BR-DE-2 und BR-DE-15 plus ein beratender information-Hinweis, der den Exit-Code nie bewegt. Verlassen Sie sich in Skripten auf das Feld valid oder den Exit-Code, nicht auf den menschenlesbaren Text.

CI-Anbindung: kein Build mit kaputter Rechnung

Für ein Repository voller Rechnungen gibt es ein fertiges Gate-Skript (POSIX sh, keine Abhängigkeiten außer python3): Es prüft rekursiv jede *.xml-Datei, lässt den Build bei jeder fatalen Verletzung mit der Regel-ID im Log fehlschlagen und schreibt pro Rechnung einen JUnit-Report, den CI-Oberflächen als Testergebnis anzeigen. Das Werkzeug ist noch nicht auf PyPI — vendoren Sie das Produktverzeichnis (z. B. nach third_party/einvoice/) und installieren Sie es im CI-Job:

python3 -m pip install ./third_party/einvoice

Dann das Gate über Ihre Rechnungsdateien laufen lassen:

sh third_party/einvoice/ci/validate-invoices.sh invoices/

Kopierfertige GitHub-Actions- und GitLab-CI-Definitionen liegen daneben im CI-Rezept (einvoice/ci/); eine uses:-pinnbare GitHub Action annotiert Befunde per SARIF direkt im Pull Request. Jedes Kommando auf dieser Seite ist byte-identisch mit den englischen Anleitungen, deren Kommandos die Testsuite gegen die echte Engine ausführt — die Doku kann nicht von dem abdriften, was das Werkzeug wirklich tut.

Weiterführend

  • Im Browser validieren — dieselbe Engine läuft per WebAssembly (Pyodide) direkt im Browser: Rechnung auswählen, Befunde lesen, nichts installieren. Die Rechnung verlässt Ihren Rechner nie; nur die Laufzeit wird nach einem Klick einmalig geladen (~13 MB).
  • Regel-Referenz — jede der 288 Regeln mit eigener Seite: Anforderung, BT-/BG-Begriffe, XML-Position, Korrekturhinweis auf Englisch und Deutsch, wörtlicher offizieller Schematron-Assert. Eigene deutsche Regelseiten gibt es bewusst nicht — der deutsche Text steht auf jeder Regelseite und in der CLI unter --lang de.
  • Praxisbeispiel — Schritt für Schritt — dieselbe kaputte Rechnung von oben, vom roten CI-Lauf zur bestandenen Prüfung, auf Deutsch (auch als englische Fassung).
  • Lizenz — Apache-2.0 für alle, auch für Closed-Source-Einbettung; die optionale kommerzielle Lizenz ($29 / $290) kauft Support und Update-Hinweise, nie die Nutzungserlaubnis.
  • English overview — die ausführliche englische Produktseite mit der vollständigen Abdeckungs-Geschichte und den Sicherheitsdetails zum Parsen nicht vertrauenswürdiger XML-Eingaben.
